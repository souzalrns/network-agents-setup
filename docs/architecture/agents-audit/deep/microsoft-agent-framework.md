## 3. Classificação e porquê

**EXTRACT** (primário) + **REFERENCE** (secundário).

Não é ADOPT nem ADAPT — a regra do nosso setup (contratos Plan-Execute próprios + MCP produção Python, não substituir por um framework) elimina essas opções por definição, e o projecto é multi-linguagem (.NET-first em cultura de API) com superfície gigante (40+ pacotes: Cosmos, Purview, Bedrock, Telegram, Copilot Studio…) desproporcional ao que precisamos.

Não é REJECT — maturidade real e verificada (13,6k estrelas, 260+ contribuidores, CI com 39 workflows verdes, releases semanais), com pelo menos 3 padrões concretos (O20, O21, O22) diretamente relevantes a lacunas já identificadas em `GOV-FASE1.md`.

É também REFERENCE para a questão arquitetural mais ampla: MAF é prova viva de que "grafo com superstep + checkpoint + HITL" é um desenho validado por uma equipa grande com produção real por trás — reforça (não substitui) a decisão já tomada neste repo de seguir o mesmo género de desenho (LangGraph já cumpria este papel; MAF é um segundo ponto de dados independente que chega à mesma forma).

## 4. O que NÃO adotar

1. **A alegação de "checkpoint = durável/tolerante a falhas"** — sem lease, sem lock distribuído, sem detecção de heartbeat; dois processos podem retomar o mesmo `checkpoint_id` em simultâneo. Se implementarmos checkpoint no `plan_runner`, precisamos do nosso próprio mecanismo de lease/fencing.
2. **Vendor lock-in Azure para durabilidade "a sério"** — durabilidade real exige o "Azure Durable Task Scheduler" como backend.
3. **A alegação de "API 1.0 estável"** — dois commits `[BREAKING]` no dia da auditoria, meses depois do anúncio de "1.0 estável".
4. **Adotar o framework inteiro como runtime** — superfície enorme e heterogénea em maturidade.
5. **Confiar em "suporte a distributed runtime" antes de existir** — maintainer confirma publicamente que ainda não existe.
6. **O viés Azure-first na documentação/exemplos** — filtrar o acoplamento a `FoundryChatClient`/Azure que aparece por defeito no README e nos quickstarts.
